# Implementation Plan — Platform Extensions
*Created: 2026-05-08*  
*Based on: `docs/next-steps/proposal.md`*

---

## Guiding Principles

1. **Fixes before features.** The issues in `fixes.md` (especially Fix 1 — Postgres blocking) should be resolved before Phase 9 work begins. They are small in scope and prevent technical debt from compounding.
2. **Each phase is independently shippable.** No phase depends on the next being complete.
3. **LLM usage stays bounded.** Every LLM-generated output goes through the existing validate → repair loop. No new "magic" paths.
4. **No new mandatory dependencies.** New framework support and export targets are opt-in via extras or lazy imports.

## Phase 8 — Framework Expansion + Scaffold Fallback ✅ Complete

*Proposal features: 3, 4*  
*Estimated effort: 3–4 weeks*

### Goal
Make the CLI useful for the majority of real-world models, not just sklearn.

### 8.1 — Multi-framework inspector

Extend `app/cli/core/inspector.py` to detect and extract metadata for:

| Framework | Detection | Metadata extracted |
|---|---|---|
| PyTorch (`nn.Module`) | `isinstance(obj, torch.nn.Module)` | layer count, input/output shapes if available |
| Transformers (`PreTrainedModel`) | `transformers` class hierarchy | model type, task, tokenizer class |
| XGBoost | already partial — complete it | n_estimators, feature count, objective |
| LightGBM | `lgb.Booster` or `LGBMModel` | n_estimators, feature count |
| CatBoost | `CatBoost` base class | feature count, loss function |
| ONNX | `.onnx` file extension | input/output names and shapes from graph |
| sentence-transformers | `SentenceTransformer` class | model name, embedding dim |

All detections use lazy imports — no new hard dependencies.

### 8.2 — Framework-specific prompt templates

Extend `app/cli/core/prompts.py` with per-framework prompt sections. Each template provides the LLM with:
- the correct `load()` pattern for that framework (e.g. `torch.load` vs `AutoModel.from_pretrained`)
- the expected `predict()` signature and tensor handling
- common preprocessing assumptions (tokenization for transformers, numpy conversion for torch)

### 8.3 — Graceful scaffold fallback (Proposal Feature 4)

When a framework is unrecognised or generation fails after max retries, instead of raising an error, write a scaffold `definition.py` with:
- correct file structure
- `# TODO` comments at every unresolved point
- inline hints based on whatever metadata was extracted

The scaffold is valid Python that imports correctly but raises `NotImplementedError` at runtime until filled in. The CLI prints a clear message: `"Scaffold written. Complete the TODOs before deploying."`

### 8.4 — Tests

Add `tests/test_cli_phase8_frameworks.py` covering:
- inspector detection for each new framework (using mock objects, no real model weights)
- scaffold generation path
- prompt template rendering for each framework type

### Deliverables
- Updated `inspector.py` with 7 new framework detectors
- Updated `prompts.py` with per-framework templates
- Scaffold writer path in `writer.py`
- New test file

## Phase 9 — Deployment Packaging + Multi-Platform Export

*Proposal features: 1, 2*  
*Estimated effort: 4–5 weeks*

### Goal
Turn a deployed model into a portable artifact that can be shipped to any target environment without manual repackaging.

### 9.1 — Packaging generator (Proposal Feature 2)

New command:

```bash
inference-engine package models/sentiment/v1/
```

Generates in the model directory:

```
models/sentiment/v1/
├── definition.py          (existing)
├── Dockerfile             (generated)
├── requirements.txt       (generated — pinned, from current venv)
└── deployment.json        (metadata: name, version, framework, device, created_at)
```

`Dockerfile` is template-based (not LLM-generated). It uses the official Python slim image, copies the model directory and artifact, installs `requirements.txt`, and starts uvicorn. Template is parameterised by Python version, device (cpu/gpu base image), and port.

`requirements.txt` is generated by inspecting the model's framework imports and pinning versions from the current environment. No LLM involved.

Implementation: new `app/cli/commands/package.py` + `app/cli/core/packager.py`.

### 9.2 — Multi-platform export (Proposal Feature 1)

New command:

```bash
inference-engine export models/sentiment/v1/ --target sagemaker
```

Supported targets and their outputs:

**`sagemaker`**
```
export/sentiment-v1-sagemaker/
├── model.tar.gz           (model artifact + inference.py)
└── inference.py           (SageMaker-compatible handler: model_fn, predict_fn)
```

**`bentoml`**
```
export/sentiment-v1-bentoml/
├── service.py             (BentoML Service class wrapping the pipeline)
├── bentofile.yaml
└── requirements.txt
```

**`ray`**
```
export/sentiment-v1-ray/
├── deployment.py          (Ray Serve Deployment class)
└── requirements.txt
```

**`replicate`**
```
export/sentiment-v1-replicate/
├── predict.py             (Replicate Predictor class)
├── Dockerfile
└── replicate.yaml
```

**`docker`** (standalone, no platform SDK)
```
export/sentiment-v1-docker/
├── Dockerfile
├── requirements.txt
└── app/                   (minimal FastAPI wrapper, not the full engine)
```

All exporters are template-based. Templates live in `app/cli/core/templates/<target>/`. The LLM is used only to fill in the `predict()` body when the target format requires a different calling convention than the engine's pipeline — and only if the existing `definition.py` doesn't already have a clean `predict()`.

Implementation: new `app/cli/commands/export.py` + `app/cli/core/exporters/` (one file per target, all implementing a common `BaseExporter` ABC).

### 9.3 — Tests

`tests/test_cli_phase9_package.py` — packaging output structure, Dockerfile content, requirements generation  
`tests/test_cli_phase9_export.py` — each exporter produces correct file structure (no real Docker build needed, just file assertions)

### Deliverables
- `app/cli/commands/package.py`
- `app/cli/core/packager.py`
- `app/cli/commands/export.py`
- `app/cli/core/exporters/` (base + 5 target exporters)
- `app/cli/core/templates/` (Dockerfile and service templates per target)
- Two new test files

## Phase 10 — Developer Experience

*Proposal features: 7, 9, 10, 6*  
*Estimated effort: 3–4 weeks*

### Goal
Reduce friction at every point where a developer interacts with the platform.

### 10.1 — Automatic sample payload inference (Proposal Feature 9)

Extend the inspector to produce a `suggested_sample_input` alongside metadata. Rules:

- sklearn with `n_features_in_`: generate a list of `n_features_in_` zeros
- text pipeline (TfidfVectorizer, CountVectorizer detected): suggest `"sample text"`
- transformers: suggest `"The quick brown fox"`
- image model (detected via layer names): suggest `{"image": "<base64 placeholder>"}`
- fallback: `null` with a hint string

This feeds into the deploy flow's sample input prompt — if a suggestion exists, it is shown as the default and the user can accept or override.

### 10.2 — Client SDK snippet generator (Proposal Feature 10)

New command:

```bash
inference-engine snippets sentiment:v1
```

Prints (or writes to `--output snippets/`) ready-to-use client code:

- `curl` — with correct headers, URL, and sample payload
- `python` — using `httpx` or `requests`
- `javascript` — using `fetch`

Templates are static with variable substitution (model name, version, host, sample payload). No LLM needed.

### 10.3 — Explain mode (Proposal Feature 7)

Add `--explain` flag to `inference-engine deploy`:

```bash
inference-engine deploy model.pkl --explain
```

After generation, before the preview, print a structured explanation block:

```
Framework detected:  sklearn (LogisticRegression)
Detection method:    class name + fit_params inspection
Features inferred:   20 (from n_features_in_)
Classes inferred:    ['negative', 'positive']
Prompt template:     sklearn/classifier
Generation attempt:  1 (no repair needed)
Validation:          passed (predict returned str in 12ms)
```

This is assembled from data already collected during the deploy flow — no extra LLM calls. It is purely a display change in `deploy.py`.

### 10.4 — Hot reload endpoint (Proposal Feature 6)

New admin endpoint:

```http
POST /admin/reload
```

Required scope: `admin`

Behaviour:
1. Calls `registry.clear_cache()` — evicts all loaded pipelines
2. Re-runs `registry.warm_up()` — reloads all registered definitions
3. Reloads `app/config/routing.py` — picks up any routing changes
4. Returns `{"reloaded_models": [...], "routing_updated": true}`

This requires adding a `clear_cache()` method to `ModelRegistry` and making `warm_up()` idempotent (it already is, based on the current implementation).

New route file: `app/adapters/http/routes/admin.py`.

### Deliverables
- Updated `inspector.py` with payload suggestion logic
- `app/cli/commands/snippets.py`
- `--explain` flag in `deploy.py`
- `app/adapters/http/routes/admin.py` with `/admin/reload`
- `ModelRegistry.clear_cache()` method
- Tests for each

## Phase 11 — Operational Maturity

*Proposal features: 8, 11, 12*  
*Estimated effort: 2–3 weeks*

### Goal
Make the platform operationally observable and self-documenting.

### 11.1 — Benchmark CLI (Proposal Feature 11)

New command:

```bash
inference-engine benchmark sentiment:v1 --host http://localhost:8000 --n 200 --concurrency 10
```

Uses `httpx` (already installed) to send N requests with the given concurrency and reports:

```
Model:        sentiment:v1
Requests:     200
Concurrency:  10
──────────────────────────
p50:          8ms
p95:          23ms
p99:          41ms
Throughput:   87 req/s
Errors:       0
Cold start:   142ms (first request)
```

Implementation: `app/cli/commands/benchmark.py`. Pure httpx + statistics, no new dependencies.

### 11.2 — Registry metadata API (Proposal Feature 12)

Extend the existing `/models` endpoint and add:

```http
GET /models/{name}/{version}/metadata
```

Returns:

```json
{
  "name": "sentiment",
  "version": "v1",
  "framework": "sklearn",
  "device": "cpu",
  "input_schema": {"type": "string"},
  "sample_input": "great movie",
  "executor": "cpu",
  "routing_strategy": "static",
  "loaded": true
}
```

This data is assembled from:
- `deployment.json` written by `inference-engine package` (if present)
- `ExecutionPolicy` config
- `RoutingService` config
- Registry warm cache state

New route: `app/adapters/http/routes/models.py` extended, or a new `metadata.py` route.

### 11.3 — Artifact fingerprinting + generation cache (Proposal Feature 8)

Cache LLM generation results keyed by:
- SHA-256 of the artifact file
- framework detected
- prompt template version (a constant bumped manually when prompts change)

Cache stored at `~/.inference-engine/cache/<hash>.json`. On deploy, if a cache hit exists, show it and ask: `"Cached generation found. Use it? [Y/n]"`. In CI mode (`--yes`), always use cache.

Cache is invalidated automatically when the prompt template version changes. No TTL needed — artifacts are immutable.

Implementation: `app/cli/core/cache.py` (~50 lines).

### Deliverables
- `app/cli/commands/benchmark.py`
- Extended models route with metadata endpoint
- `app/cli/core/cache.py` integrated into deploy flow
- Tests for benchmark output format, metadata endpoint, cache hit/miss

## What We Are Not Building

These items from the proposal are deferred indefinitely:

- **Playground UI (Feature 5):** FastAPI's auto-generated `/docs` (Swagger UI) already provides interactive testing. A custom playground adds frontend complexity for marginal gain over what already exists. Revisit if there is a specific use case that Swagger doesn't cover.
- **Replicate export:** Replicate's format changes frequently and their target audience (hobbyist GPU hosting) doesn't align with the platform's production focus. Can be added later as a community contribution.
